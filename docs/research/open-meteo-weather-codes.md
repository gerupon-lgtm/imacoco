# Open-Meteo `weather_code` 調査

- 確認日: 2026-08-12
- 対象: Open-Meteo Weather Forecast API の `current.weather_code` と `hourly.weather_code`
- 調査方針: Open-Meteo公式ドキュメント、Open-Meteo公式GitHubリポジトリだけを一次資料として使用

## 結論

1. Open-Meteoが現在公式ドキュメントに掲載している `weather_code` は、7種類ではなく**28個の数値コード**である。
2. いまここインフォの7種類は、28コードを見分けやすい図柄へまとめた**アイコン分類**である。表示文言は10種類に集約している。
3. 現行実装は、公式表にある28コードをすべて表示文言とアイコンへ割り当てている。既知のコードが未対応のため「くもり」アイコンになる箇所はない。
4. Open-Meteoから届くのは「雷」「雷雨」のような文字列ではなく、数値の `weather_code` である。現行アイコンは表示文言ではなく数値コードから選ぶため、文言が「雷」に変わってもコード95・96・99であれば雷アイコンにできる。
5. 公式表には「雷雨」という名称のコードはない。コード95は `Thunderstorm: Slight or moderate`、96・99はひょうを伴う雷雨である。現行の「雷雨」はアプリ側の日本語集約であり、公式の意味を厳密に残すなら95を「雷」、96・99を「雷・ひょう」などへ分ける余地がある。
6. 将来追加された未知コードは、現行実装では表示文言が「天気情報」、アイコンが `cloud` になる。アプリが誤って文字列の「雷」を受け取り「くもり」と表示することはないが、未知の重大現象を雲アイコンに見せる可能性は残る。

公式ドキュメントは、ひょうを伴う雷の予報は中央ヨーロッパだけで利用できると注記している。日本国内専用の本アプリでは96・99の出現は想定しにくいが、現行実装は両方に対応している。

### 数と分類

- 公式コード: 28個
- 現行の表示文言: 10種類
  - 快晴、晴れ、晴れ時々くもり、くもり、霧、霧雨、雨、雪、にわか雨、雷雨
- 現行のアイコン: 7種類
  - `sun`、`partly-cloudy`、`cloud`、`fog`、`rain`、`snow`、`thunderstorm`

したがって、「天気が7種類しかない」のではなく、「28コードを7種類の図柄へ意味の近い単位で集約している」が正確である。

## 「雷」というステータスが来る可能性

Open-Meteo公式仕様では `weather_code` は数値で返り、「雷」や「雷雨」という文字列は返らない。コード95の公式説明は `Thunderstorm: Slight or moderate` なので、意味としては「雷」に相当するコードがすでに存在する。ただし、現行実装はコード95を明示的に `thunderstorm` アイコンへ割り当てている。

現行処理は次の順序である。

1. `src/providers/openMeteo.ts` が数値の `weather_code` を検証する。
2. 同ファイルの `weatherCodeLabel()` が数値コードから日本語文言を生成する。
3. `src/components/WeatherStateIcon.tsx` の `weatherIconName()` が、同じ数値コードからアイコンを選ぶ。

表示文言からアイコンを逆引きしていないため、「雷」という文字列と「雷雨」という文字列の不一致で雲アイコンになる構造ではない。

## 公式一覧の完全性について

Open-MeteoのWeather Forecast APIドキュメントは `weather_code` を「数値コード」と説明し、詳細として28コードの表を掲載している。現時点でOpen-Meteoが公開しているコード一覧としては、この表が正典である。

ただし、公式OpenAPI定義のレスポンス型は `weather_code` を単なる `integer` とし、許可値の `enum` を定義していない。そのため、次の区別が必要である。

- **人が読む現行仕様**: 公式ドキュメントの28コード表が完全な一覧として機能する。
- **機械可読な契約**: OpenAPIだけでは28コード以外を禁止しておらず、将来コード追加を自動検出できない。

また、複数地点・複数日を実際のAPIへ問い合わせて現れたコードだけを収集する方法では、稀な現象や地域限定コードを見落とす。実測サンプリングは動作確認には使えるが、全コードの証明にはならない。

## 現行実装の評価

### 問題なし

- `weatherCodeLabel()` は公式28コードをすべてカバーしている。
- `compactWeatherCodeLabel()` も公式28コードをすべてカバーしている。
- `weatherIconName()` も公式28コードをすべてカバーしている。
- 95・96・99はすべて専用の `thunderstorm` アイコンになる。
- 未知コードを受けても例外で天気カード全体を落とさず、汎用表示へ退避する。

### 改善候補

1. **コード表を1か所へ統合する**
   - 現在は表示文言とアイコンのコード集合が別ファイルに重複している。
   - 1つの `weatherCodeDetails` 定数から詳細文言、短縮文言、アイコンを導出すれば、将来片方だけ更新し忘れる事故を防げる。
2. **全28コードの網羅テストを持つ**
   - 公式コード配列をテストの入力にし、各コードに詳細文言、短縮文言、アイコンが必ずあることを検査する。
   - 現行のアイコンテストは分類の代表コードが中心なので、全28件の表駆動テストへ広げる価値がある。
3. **未知コードを雲と断定しない**
   - 現在の未知コードは `cloud` になるため、将来の新しい重大現象を「くもり」の図柄に見せる可能性がある。
   - 「不明な天気」を示す中立アイコン、またはアイコン非表示＋「天気情報」とする方が誤認を抑えられる。
4. **雷の文言を公式意味に近づけるか判断する**
   - 95を「雷」、96・99を「雷・ひょう」とすれば意味の保持率は上がる。
   - ただし日本国内専用かつ一画面でざっくり示す製品方針では、同一の雷アイコンにまとめること自体は合理的である。

## API仕様変更を検知する方法

Open-Meteoには、`weather_code` の数値集合だけをバージョン付きで配布する機械可読なenumは確認できなかった。次の二段構えを推奨する。

### 1. 公式ソースの変更を追う

公式サイトのコード表はOpen-Meteo公式GitHubリポジトリ内の次のファイルにある。

- [`src/routes/en/docs/+page.svelte`](https://github.com/open-meteo/open-meteo-website/blob/main/src/routes/en/docs/%2Bpage.svelte)
- [同ファイルのコミット履歴](https://github.com/open-meteo/open-meteo-website/commits/main/src/routes/en/docs/%2Bpage.svelte)

リリース前や定期保守時に、このファイルの `WMO Weather interpretation codes (WW)` 部分とアプリのコード集合を比較する。GitHub上で公式リポジトリをWatchする方法も補助になるが、リポジトリ全体の通知であり、コード表だけの専用通知ではない。

### 2. 外部依存の定期チェックを通常テストから分離する

将来、自動化するなら、週次または月次のスケジュール実行で公式ソースを取得し、期待するコード集合

```text
0, 1, 2, 3, 45, 48, 51, 53, 55, 56, 57,
61, 63, 65, 66, 67, 71, 73, 75, 77, 80, 81,
82, 85, 86, 95, 96, 99
```

との差分を検査する。外部サイトの一時障害やHTML変更で通常のビルドを止めないため、`npm run check` へ常時組み込まず、手動実行可能な別スクリプトと定期ワークフローに分けるのが安全である。

公式OpenAPI定義も併せて監視すれば、フィールド名や型の変更は検知できる。ただし、現在のOpenAPIはコード値のenumを持たないので、OpenAPIだけでは新しい数値コードの追加を検知できない。
